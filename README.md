## Software supply chain evidence checklist

For an important software dependency or ICT supplier, consider whether you can obtain and re-check:

- [ ] supplier/operator identity
- [ ] product or software identity
- [ ] current version/release
- [ ] SBOM availability
- [ ] dependency inventory
- [ ] release provenance
- [ ] vulnerability-management contact
- [ ] security/advisory location
- [ ] lifecycle / end-of-support information
- [ ] incident contact
- [ ] evidence timestamp/freshness
- [ ] current public evidence location

---

## SBOM review is more than file presence

The useful questions include:

- Which product/release does the SBOM describe?
- When was it generated?
- Which component inventory is represented?
- Can the supplier or operator be identified?
- What happens when the product changes?
- Can a relying party re-check evidence later?

An SBOM is evidence. It is not automatically proof that software is secure.

## DORA-related evidence

DORA creates important operational-resilience and ICT third-party evidence requirements for in-scope financial entities and suppliers.

ECZ-ID positions its DORA-related products as evidence infrastructure and operational support.

This repository must not be read as certification or a guarantee of DORA compliance.

## Resolver-first evidence

A reusable evidence model should make it possible to:

1. identify the supplier or software surface
2. link relevant evidence
3. show freshness and lifecycle state
4. preserve machine-readable references
5. let the relying party apply its own policy
